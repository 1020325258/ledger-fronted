# fund-ledger-frontend

统一资金账本的应用层 UI，面向**服务者**和**客户本人**，把 `nrs-order-service` 的
`/ledger/project` 返回的账本解释成「一次业务操作把钱从哪挪到哪」。

## 设计原则

1. **后端已经组装好账本，前端只负责呈现。**
   `transferGroupId` 的跨池配对、`fundActionDesc` 的中文文案、`poolTypeDesc`、
   逐池 `balanceVerify`、跨组 `groupVerifySummary` 全部是后端权威结论。
   前端不推导连边、不猜对手方、不做可信度降级、不重算校验。

   前端的派生动作全在 `src/groups.ts`，只有两处：按 `transferGroupId` 归并 + 按
   `direction` 拆出入金腿；以及 `groupEdges()` 在账本能唯一确定时导出池间连边
   （详见下方「资金流向图」）。金额按「分」整数累加，避免浮点漂移。

2. **第一公民是「一次资金操作」，不是「一条账本条目」。**
   一笔支付分摊到 3 个去处，是一行、展开看分摊；不是三行让人误读成付了三笔。

3. **服务者和客户看同一套页面，不分视角。**
   侧边栏 5 个视图全部展开，字段一律展示（含源表、原始码、校验），
   不用两套组件、也不做隐藏。

4. **枚举一律翻成业务话术，口径镜像后端枚举的 `desc`。**
   映射集中在 `src/codes.ts`，注释里写明对齐哪个后端源文件。

## 视图

侧边栏是**视图切换器**，不是页内锚点目录；每个视图自己控制高度。

| 视图 | 说明 | 图 |
|---|---|---|
| 资金总览 | 投入 / 已退回（含系统内回流）/ 系统内余额 / 待付 | **资金存放树图** + **余额演变堆叠面积图** |
| 资金流水 | **主视图**。一行 = 一次操作，按天倒序，可按支付/抵扣/退款筛选 | |
| 资金流向 | 逐池的入金从哪来、出金到哪去 + 余额校验 | **泳道时序流向图**，池展开处有**余额瀑布图** |
| 订单与款项 | 整装款项拆到子款项的应收/实收/待付；商品订单按 CT 组合单归集 | |
| 对账与校验 | 顶层守恒 + 逐池余额 + 跨组守恒 + 归属告警 | |

## 四张图，四个问题

| 图 | 回答的问题 | 维度 | 位置 |
|---|---|---|---|
| 资金存放树图 | 我的钱**现在**放在哪些池子里，各占多少 | 存量截面 | 资金总览 |
| 余额演变堆叠面积图 | 我的钱是**怎么攒起来**的，中间分布怎么变 | 存量时序 | 资金总览 |
| 泳道时序流向图 | **每一次操作**把钱从哪挪到哪 | 流量时序 | 资金流向 |
| 池余额瀑布图 | **这个池**的余额为什么是这个数 | 单池归因 | 资金流向（池展开） |

前两张是「钱在哪」，后两张是「钱怎么动的」；前三张是全局，最后一张是单池下钻。
四张图共用 `src/charts/layout.ts` 的几何工具与同一套配色（池类型色 + 操作性质色），
点击行为统一：点图元 → 该次操作的溯源抽屉，点池/泳道 → 跳到该池的收支明细。

### 资金存放树图（`src/charts/treemap.ts`）

Squarified treemap，面积 ∝ `FundPool.balance`。外层资金池类型、内层具体池，
子款项明细放 tooltip（第三层会把图切太碎）。只画余额为正的系统内池 ——
`CUSTOMER` / `DEVELOPER` 是系统外虚拟池、余额天生为负，放进面积图会算出负面积。

> 已知局限：占比极小的池（如 500 元的设计费 vs 10.7 万的工程款，0.47%）会退化成
> 几个像素宽的细条，只能靠 tooltip 读。树图的固有问题，不是 bug。

### 余额演变堆叠面积图（`src/charts/growth.ts`）

X 轴按交易组顺序等距（与泳道图一致），Y 轴是系统内存量，按池类型堆叠。
归集池铺在底层，形状不被上层挤压。

曾经鼓起来又归零的色带（预收款收进来又全部抵扣掉是典型）右侧没有厚度可标，
峰值处放一个标记点，说明文字放到图下的注释行 —— 压在色带上的小字无论怎么描边都读不清。

**自校验**：算法只是按时间对条目做累加，而后端契约是「池余额 = 池内条目金额之和」，
所以累加终值必须等于各池 `balance` 之和。图下角把这个比对结果标出来，对不上就报差额。

### 池余额瀑布图（`src/charts/waterfall.ts`）

池卡片展开处。池内条目按时间排开，柱子首尾相接，最后落在池余额上。
对 S14…1381 这种「付进来 8,400 → 减项退出去 8,400 → 预收款抵回 10,200」的池最有解释力，
三根柱子直接把余额 10,200 的来历讲清楚。同样带累加终值 vs `pool.balance` 的比对。

### 泳道时序流向图（`src/charts/flowmap.ts`）

放在「资金流向」视图顶部，池卡片在下。

- **Y = 资金池泳道，X = 时间**（按交易组顺序等距排列，不按真实时间间隔，否则跨月的空白会把图撑散）
- **一列 = 一个交易组**，所以点列上任何位置都打开该次操作的溯源抽屉；点泳道名展开下方对应池账本
- 箭头指向收钱的一方，线宽 ∝ 金额，颜色按操作性质（支付/抵扣/退款）与流水视图一致
- 泳道粒度可切「按类型」（默认，4~6 条）/「按资金池」；按池时同一 CT 单的 S 单相邻排列以缩短连线

**为什么不是桑基图**：预收款与商品子单之间存在互为反向的边（减项退回 8,400、抵扣回去 10,200），
这是家装资金的典型形态。桑基和一切 DAG 布局不支持环，而净流向画法会把「退回来又用掉」整段抹掉 ——
客户就永远看不到自己那 8,400 去哪了。泳道图里环在时间轴方向自然展开。

**连边怎么来的**：`groups.ts` 的 `groupEdges()`。账本记的是「这些池出了多少、那些池进了多少」，
没有记「哪笔出金对应哪笔入金」。所以只有当一侧只涉及 1 个池时，连边才被账本唯一确定 ——
另一侧每条腿的原始金额就是那条边的金额。两侧都 ≥2 个池时返回 `null`，图上不画并如实说明，
绝不按比例瞎分。实测 2872 / 1111 两单共 23 个组，需要返回 `null` 的是 **0 个**。

单边组与断链组（如 `…1111` 那单 9 个组全部只有一侧记录）没有边，图会说明「画不出流向图」及原因，
而不是显示一张空白图。

**溯源抽屉**贯穿所有视图：点任意一笔操作，右侧滑出业务动作（售后单/变更单/交易号）、
出入金腿、源表记录 ID，以及「这笔钱进入的资金池之后的出金操作」。

## 目录结构

```
src/
  api.ts            数据层：DTO 类型、请求、URL 状态（可分享）
  codes.ts          码表层：枚举名与数字码 → 业务话术，镜像后端枚举 desc
  groups.ts         交易组视图模型（薄）+ 资金池展示信息
  context.ts        ViewContext：一次查询的结果与跳转能力
  drawer.ts         溯源抽屉
  charts/
    layout.ts       squarified treemap 布局、金额缩写、色阶
    flowmap.ts      泳道时序流向图
    treemap.ts      资金存放树图
    growth.ts       余额演变堆叠面积图
    waterfall.ts    池余额瀑布图
  views/
    overview.ts     资金总览（树图 + 余额演变）
    stream.ts       资金流水（主视图）
    pools.ts        资金流向（流向图 + 逐池账本 + 瀑布图）
    orders.ts       订单与款项
    verify.ts       对账与校验
  main.ts           外壳：侧边栏 + 查询条 + 视图路由
  style.css         样式
```

## 本地运行

```bash
npm install
npm run dev
```

Node.js ≥ 18。访问 <http://127.0.0.1:5173>，输入主单号查询。

**环境选择要注意**：默认打的是 `localhost:6881`（本地后端）。要打预发请在页面上选
「预发 preview」，或在 URL 上带 `env=preview`。代理配置见 `vite.config.ts`。

### 可分享链接

```
http://127.0.0.1:5173/?projectOrderId=826061315000002872&env=preview&view=stream
```

参数：`projectOrderId` / `env`（localhost·escrow·preview）
/ `view`（overview·stream·pools·orders·verify）/ `verify`。

## 接口

```bash
curl 'http://preview-nrs-order-service.home.ke.com/ledger/project?projectOrderId=<主单号>&verify=true&groupByPool=true' \
  -H 'X-NRS-User-Id: 1000000000000000'
```

页面固定用 `groupByPool=true`：池维度的 `subFunds`、`balanceVerify`、`compositOrderNo`
是主要素材，平铺明细可以从池里取到，反之不行。

## 接口待补字段（UI 层已按占位实现，等后端补齐）

按当前返回值能做到的都做了；下面这些缺口会限制「对客可解释」的深度。

**一、枚举描述没输出，前端只能镜像枚举**

| 缺口 | 现状 | 影响 |
|---|---|---|
| `groupTypeDesc` | `LedgerGroupType.desc`（"预收款抵扣" 等）后端有，`PoolEntry` 只序列化枚举名 | 这是旧版 UI 直接漏出 `ADVANCE_DEDUCT` 的原因 |
| `pairingStatus` / `pairingReason` 的 desc | `metadata` 里只有 code | 服务者排查断链要自己记 code |

**二、`metadata` 里的数字码没有中文**

`cashierType` / `changeSource` / `flowType` / `refundMode` / `changeType` / `tradeType`
目前靠前端 `codes.ts` 本地码表翻译，存在与后端不同步的风险。

> 顺带一个后端不一致：`PayInfoCustomerOutflowScenario.cashierDesc()` 是一份硬编码
> switch，与 `PaymentCashierTypeEnum` 对不上 —— `cashierType=2` 在枚举里不存在，
> 但 scenario 映射成「微信」（实测数据里确实有 2）。建议统一到枚举。

**三、业务语义缺失（客户最关心的部分）**

| 缺口 | 客户答不了的问题 |
|---|---|
| S 单池没有商品名 / 品类摘要 | "这笔钱买了哪些商品？" |
| `item_change_record` 只给 `projectChangeNo` + `changeType`，没有变更原因和商品明细 | "为什么给我退了 8,400？减的是什么？" |
| `OrderRefundMetadata` 没有售后单当前状态 | "我的退款到哪一步了？" |
| `SUB_ORDER` 池只有 `balance`（实收），没有应付 | "这个商品订单我还要付多少？"（目前「待付」只能算整装款项） |

**四、小口径问题**

- `FUND` 池的 `poolTypeDesc` 与 `fundName` 是同一个值（都为「工程款」），前端要去重才不显示成
  「工程款·工程款」。建议 `poolTypeDesc` 固定为池类型「整装款项」。
- 一个交易组的两腿时间可以差几分钟（实测退款组出金 13:43:40 / 入金 13:49:18）。
  前端取最早时间作为操作时间；若要展示「退款发起 → 到账」的过程，需要状态时间戳。

## 相比旧版的变化

- 删掉 `flow.ts`（431 行）+ `flowview.ts`（563 行）+ `views.ts`（568 行）。
  前两个是在前端重新推导池间连边并标注「可信度」，与「后端已配对」的契约重复。
- 修掉三个语义错误：一次支付被拆成多行、对手方把同方向的腿也列进去（"去向：客户钱包"）、
  「已退回 0.00」掩盖了系统内回流。
- 单页 9,400px 长滚动 → 5 个视图各自一屏 + 溯源抽屉。
- 不再依赖 ECharts（`package.json` 里的 `echarts` 已无引用；余额分布用 CSS 条形，流向图自绘 SVG）。
- 去掉客户/服务者视角切换：侧边栏 5 个视图全部展开，字段一律展示。
- 图从 1 张（旧版的绕线流向图）变成 4 张，各答一个不同问题。
